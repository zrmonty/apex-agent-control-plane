# Apex ClickHouse projection API v1

The ClickHouse writer is a projection service, not a public database endpoint.
It accepts only authenticated HTTPS requests from the ingest/forwarder identity,
validates the complete `apex.v1.EventEnvelope`, and inserts the typed columns
defined in [`deploy/clickhouse/schema.sql`](../../deploy/clickhouse/schema.sql).

## Event write

```http
POST /v1/events
Content-Type: application/x-protobuf
X-Apex-Event-Id: {event_id}
X-Apex-Event-Hash: {event_hash}

<validated apex.v1.EventEnvelope protobuf bytes>
```

The service must verify both headers match the envelope, recompute and verify
`integrity.event_hash`, enforce the 256 KiB envelope limit, and derive workspace
and namespace exclusively from the validated envelope. Caller-supplied SQL,
table names, filters, or raw event text are never interpolated into the insert.

The writer stores both typed query columns and the compressed original protobuf
bytes. `data_json` is the bounded, validated JSON representation of `data`; it
is not a command or an executable expression. The canonical archive remains the
immutable provider record, not a ClickHouse row.

## Idempotency and conflicts

`(workspace_id, namespace_id, event_id)` is the logical idempotency key and
`event_hash` is the payload fingerprint. A repeated event ID with the same hash
is an acknowledged duplicate. A repeated event ID with a different hash returns
`409 Conflict`, creates a security/audit finding, and must not overwrite either
payload. Because ClickHouse merges asynchronously, point lookups that need this
guarantee use `FINAL` and treat multiple hashes for one logical key as a conflict.

## Response policy

| Status | Meaning | Retry |
|---|---|---|
| `201`/`204` | Insert accepted or same-hash duplicate acknowledged | No further write |
| `400`/`413` | Invalid schema, integrity, scope, or size | Never |
| `401`/`403` | mTLS/bearer or scope authorization failure | Never until configuration changes |
| `409` | Event-ID idempotency conflict | Never; preserve evidence and alert |
| `429`/`5xx`/timeout | Bounded provider capacity or transient failure | Yes, through the 1–8 attempt durable retry policy |

Responses must not echo protobuf bytes, credentials, SQL, or untrusted event
content. The service emits only the project’s redacted diagnostic error shape.

## Diagnostic error shape

Clients cap provider response bodies at 64 KiB and discard them after
classification. Malformed JSON, duplicate headers, or an oversized response
is a terminal `PUBLISH_FAILED` protocol error and is never copied into a
retry decision or diagnostic text.

Every non-success response uses a stable code and safe human-readable text.
When a body is returned it is bounded JSON:

```json
{"code":"INVALID_ENVELOPE","summary":"The event envelope failed validation.","cause":"The event hash does not match the canonical bytes.","retryable":false,"correlation":{"event_id":"00000000-0000-7000-8000-000000000001"},"next_steps":["Recompute the event hash and retry once corrected."]}
```

Codes are `INVALID_ENVELOPE`, `PAYLOAD_TOO_LARGE`,
`INVALID_SINK_CONFIGURATION`, `IDEMPOTENCY_CONFLICT`, and `PUBLISH_FAILED`.
All text is bounded and sanitized: never include protobuf fields, SQL,
credentials, URLs, response bodies, or arbitrary provider text. Include an
event ID only after UUID validation and use a separate opaque server
correlation ID for logs. Retryability is derived from the status table, never
from caller/provider JSON. An unexpected 2xx missing a required acknowledgement
is a terminal protocol failure.

The writer must not partition or allocate storage directly from unbounded,
caller-controlled timestamps. Use server ingestion time for physical partitioning
(as in [`schema.sql`](../../deploy/clickhouse/schema.sql)); retain event time as
a validated query column. `ingested_at` is materialized by ClickHouse and cannot
be supplied by the event writer. Query endpoints must apply the authenticated caller's
workspace/namespace scope before execution and enforce bounded rows, bytes, and
time range limits.
