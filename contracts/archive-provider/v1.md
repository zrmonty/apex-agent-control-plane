# Apex archive-provider API v1

This is the provider-neutral contract for the compliance forwarder. The core
must not import an AWS, Azure, Laserfiche, or vendor SDK. Each adapter implements
these operations and exposes only redacted, typed failures to the control plane.

## Logical API

Every request carries an `idempotency_key` derived from the batch content hash.
The key is stable across retries and process restarts. Provider adapters must
return the same receipt for the same key and must reject a key reused with a
different content hash.

```text
write_batch(request: ArchiveBatch) -> ArchiveReceipt
apply_retention(request: RetentionRequest) -> RetentionState
apply_legal_hold(request: LegalHoldRequest) -> LegalHoldState
get_receipt(request: ReceiptRequest) -> ArchiveReceipt
verify(request: VerifyRequest) -> VerificationResult
health() -> ProviderHealth
```

`ArchiveBatch` contains:

| Field | Requirement |
|---|---|
| `batch_id` | Lowercase UUIDv7 or an adapter-generated opaque ID; never supplied by object-path text. |
| `idempotency_key` | Lowercase SHA-256 hex of the canonical manifest and event bytes. |
| `manifest` | Canonical JSON, UTF-8, with schema version, scope, event count, byte count, and event hashes. |
| `events` | Complete canonical event representations; no truncation or silent repair. |
| `content_sha256` | SHA-256 over the exact manifest-plus-event representation written to the provider. |
| `retention` | Named policy plus the requested retain-until timestamp, if required. |

Deployments must enforce request bounds before parsing or allocating: at most
1,024 events, 16 MiB total manifest-plus-event bytes, 1 MiB manifest bytes,
and 256 KiB per event. Violations are terminal validation errors; never
truncate, buffer without a limit, or trust manifest-declared sizes.

`ArchiveReceipt` must include the provider name, immutable record ID/version,
content hash, server timestamp, retention state, legal-hold state, and whether
the result was a replay of an existing write. The adapter must not report
success until the provider has acknowledged the bytes and required metadata.

## Capability and error contract

`ProviderHealth` declares, rather than infers, these capabilities:

```text
immutable_retention: required | supported | unavailable
legal_hold:          required | supported | unavailable
version_identifier:  required | supported | unavailable
read_after_write:    required | supported | unavailable
content_verification: required | supported | unavailable
```

Compliance-required deployments refuse to start unless immutable retention,
version identifiers, read-after-write, and content verification are supported
and the adapter acceptance suite passes. The forwarder identity must not have a
retention-bypass permission.

Errors are classified as `configuration`, `authentication`, `authorization`,
`conflict`, `capacity`, `transient`, or `verification`. Only `transient` and
explicitly bounded `capacity` failures are retryable. An error report includes
the operation, provider, batch ID, idempotency key fingerprint, safe cause, and
next step; it never includes credentials, raw event bytes, or provider URLs with
embedded secrets.

### Diagnostic error shape

Adapters expose the same redacted diagnostic contract as the gateway:

```json
{"code":"ARCHIVE_IDEMPOTENCY_CONFLICT","summary":"The archive contains this event ID with different content.","cause":"The provider hash differs from the requested event hash.","retryable":false,"correlation":{"batch_id":"0190abcd-1234-7abc-8def-0123456789ab"},"next_steps":["Preserve both hashes and investigate before retrying."]}
```

Stable codes are `ARCHIVE_CONFIGURATION`, `ARCHIVE_AUTHENTICATION`,
`ARCHIVE_AUTHORIZATION`, `ARCHIVE_IDEMPOTENCY_CONFLICT`, `ARCHIVE_CAPACITY`,
`ARCHIVE_TRANSIENT`, and `ARCHIVE_VERIFICATION`. Text is bounded and sanitized;
never include event bytes, manifest contents, credentials, raw provider URLs,
SQL, or unsanitized provider response text. Correlation fields are emitted only
after UUID/hash validation, with a separate opaque server correlation ID for
structured logs. Retryability comes from the classified error and status, not
provider-controlled JSON.

## Authenticated HTTP mapping

The current staging client maps one event write to:

```http
PUT /v1/events/{event_id}.pb
Content-Type: application/x-protobuf
If-None-Match: *
X-Apex-Event-Id: {event_id}
X-Apex-Event-Hash: {event_hash}

<validated apex.v1.EventEnvelope protobuf bytes>
```

The endpoint is HTTPS-only and uses mTLS, with an optional bearer token loaded
from a protected file. `{event_id}` is a validated lowercase UUIDv7 path segment;
it is never accepted as arbitrary path text. The event-hash header is the
lowercase SHA-256 fingerprint already present in the validated envelope.

Responses:

| Status | Meaning | Client behavior |
|---|---|---|
| `201` or `204` | New immutable record committed, with `X-Apex-Event-Hash` echoing the request hash | Acknowledge only after verifying the hash echo. |
| `412` | Object already exists with the same event ID and content hash, with a matching `X-Apex-Event-Hash` echo | Treat as an idempotent success only after verifying the hash echo. The provider must not use this for a hash conflict. |
| `400`/`413` | Invalid or oversized envelope | Terminal configuration/validation failure; do not retry. |
| `401`/`403` | Authentication or authorization failure | Terminal until credentials/policy are corrected. |
| `409` | Same event ID with a different content hash | Terminal idempotency conflict; alert and preserve both receipts. |
| `429`, `5xx`, or transport timeout | Provider capacity/transient failure | Retry only through the bounded durable-sink policy. |

Any `201`, `204`, or `412` response without exactly one valid matching
`X-Apex-Event-Hash` is a terminal `ARCHIVE_VERIFICATION` failure. Response
headers and bodies are bounded (64 KiB for diagnostics); malformed or
oversized responses are discarded and never treated as an acknowledgement or
used to choose retryability.

The provider must also expose a verification-capable read path to the adapter,
at minimum `HEAD /v1/events/{event_id}.pb` for receipt metadata and
`GET /v1/events/{event_id}.pb` for byte/hash verification. `GET` responses must
be bounded to the configured maximum object size, carry a content length, and
include the verified event/content hash; adapters must stream or discard bodies
without unbounded buffering. Retention and legal hold operations remain
adapter-specific and must be represented in the logical API above; a staging PUT
alone does not establish WORM guarantees.

## Acceptance tests

Every adapter must prove: duplicate write returns one logical record; changed
content under the same idempotency key is rejected; bytes and hash verify after
read-after-write; retention and legal hold read back correctly; mutation/deletion
are denied while protected; a crash between provider write and receipt
persistence can be reconciled; a forged/missing receipt hash is rejected; replay
and response ambiguity cannot produce a false acknowledgement; and an
independent verifier identity can obtain evidence without write or
retention-bypass privileges.
